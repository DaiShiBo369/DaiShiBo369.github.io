在博客中运行 Python：JupyterLite 上手笔记

Disboundary2026-07-092026-07-16

背景：博客里的代码为什么不能只停在代码块

写 Python 学习笔记时，静态代码块只能展示“我写了什么”，却不能让读者直接改一行参数、跑一次结果。对算法、数据可视化、数值实验这类内容来说，能运行的 Notebook 比截图和伪代码更接近真实学习过程。

但博客通常是静态站点。它适合发布 Markdown、图片、CSS 和 JavaScript，不适合在服务器上给每个读者启动一个 Python 进程。如果用传统 Jupyter Server，就会引入账号、权限、资源隔离、后端部署和长期维护问题。对一个个人博客来说，这个成本明显太高。

JupyterLite 正好卡在这个需求中间：它把 Jupyter 的前端、文件系统、内核通信和 Python 运行时尽量搬到浏览器里，让读者在页面中打开一个轻量的 Notebook 或 REPL，而不是连到我的服务器执行代码。

JupyterLite 是什么

JupyterLite 可以理解成“运行在浏览器里的 JupyterLab/Notebook 发行版”。它使用 JupyterLab 的前端组件，但没有传统意义上的 Python 后端服务器。Python 内核通常由 Pyodide 或 xeus-python 这类 WebAssembly 方案提供，计算发生在读者自己的浏览器里。

所以它适合的不是“把线上服务器开放给所有人算代码”，而是“把教学、演示、轻量实验打包成静态网页”。官方文档也明确强调，JupyterLite 可以通过静态 HTTP(S) 托管，并且不需要专门的应用服务器。

为什么它适合静态博客

对当前博客来说，JupyterLite 的吸引力主要有三点。

第一，它和静态站点的发布模型一致。Hexo 最终生成的是一堆静态文件，而 JupyterLite 构建后同样是一组 HTML、JavaScript、配置和资源文件。只要把构建结果放进 source/ 下的普通目录，站点生成时就能一起发布。

第二，计算压力不在博客服务器上。读者运行代码时，Python 内核在浏览器里启动。我的站点只负责分发静态资源，不需要处理用户代码执行、进程隔离或容器调度。

第三，它可以渐进接入。刚开始不必把整套 Notebook 系统做成站点主功能，只需要在某篇文章里嵌一个 REPL，等确认体验可接受后，再考虑给特定专题配套 Notebook 文件。

Notebook、Lab 和 REPL 怎么选

JupyterLite 构建后通常会提供多个入口。它们不是互相替代，而是面向不同阅读场景。

入口 适合场景 博客中的用法
lab/ 接近完整 JupyterLab 的工作区 专题实验、多个 Notebook 和数据文件
notebooks/ 打开单个 Notebook 一篇文章配一个可交互实验
repl/ 单个可执行输入区 演示短代码、函数调用、参数试验

我的第一步会优先考虑 repl/，原因是它对文章节奏影响最小。读者看到一段解释后，可以马上在旁边试一小段代码；如果直接嵌完整 Lab，界面能力更强，但也更容易抢走正文的注意力。

Python 包安装要有预期

JupyterLite 不是普通本地 Python。它的 Python 环境运行在 WebAssembly 里，所以包兼容性不能按桌面 Python 来想。

它背后会通过 piplite 和 Pyodide 的包安装机制工作。纯 Python 包通常更容易成功；依赖系统库、文件系统权限、后台服务或复杂原生扩展的包，就需要具体测试。像 numpy、matplotlib 这类常见科学计算和可视化库通常是 JupyterLite 适合演示的方向，但不能假设所有 PyPI 包都能在浏览器里跑。

因此，博客文章里如果要嵌入交互代码，最好遵守三个约束：

  • 示例代码尽量短，启动后几秒内能看到结果；
  • 依赖尽量少，能用标准库就不用额外包；
  • 需要额外包时，在正文里说明首次加载可能较慢。

文件保存和缓存也要说明白

JupyterLite 可以在浏览器里保存文件和设置，但这不是把读者的修改提交回我的博客仓库。用户修改 Notebook 后，通常会保存到浏览器自己的 IndexedDB 或 localStorage 里；如果换浏览器、清理站点数据或使用隐私模式，这些内容可能丢失。

这点在教学文章中很容易造成误解。读者看到“保存”按钮，会以为下次一定还能找回。更稳妥的表达是：JupyterLite 里的修改适合临时实验，重要结果要手动下载。

Service Worker 也需要单独注意。JupyterLite 默认会尝试使用 Service Worker 来做缓存和离线能力，但它只在浏览器支持且页面运行在 HTTPS、localhost 或 127.0.0.1 等安全上下文时可用。上线后如果发现资源更新了但页面还加载旧版本，优先检查浏览器缓存和 Service Worker。

它不适合做什么

JupyterLite 很适合“读者侧轻量计算”，但不适合所有 Python 场景。

它不适合处理私密凭据。代码在浏览器里运行，任何写进 Notebook 的 token、密钥、数据库地址都不能当成秘密。

它不适合重计算。浏览器内核的 CPU、内存和线程能力有限，长时间数值仿真、训练模型、大规模数据处理都不应该塞进博客文章。

它不适合依赖系统环境的程序。比如调用本机命令行工具、访问任意本地路径、启动后台服务、连接内网资源，这些都不是 JupyterLite 的目标。

它也不适合替代正式实验记录。真正需要可复现的科研实验，仍然应该有仓库、环境文件、数据版本和脚本入口。JupyterLite 更像是文章里的交互窗口，而不是完整研究工程。

当前结论

这次上手后，我对 JupyterLite 的定位更清楚了：它不是“把 Jupyter Server 免费塞进静态博客”，而是把一部分适合浏览器执行的 Python 学习场景，做成可以随文章一起分发的交互组件。

下一步如果继续接入当前博客，我会按这个顺序推进：

  1. 先在 source/jupyterlite/ 发布一个最小 REPL；
  2. 选一篇 Python 学习文章嵌入 iframe，而不是全站铺开；
  3. 记录首次加载速度、移动端高度、主题样式冲突和包安装体验；
  4. 再决定是否为专题文章提供配套 Notebook。

对个人博客来说，这个方案的价值不在于“功能完整”，而在于成本足够低：不用维护后端，不给服务器开放代码执行权限，也能让读者在文章现场跑几行 Python。
